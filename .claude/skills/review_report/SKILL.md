# review_report

2段レビューの**2段目**です。Claude は自分のレビューを作るだけでなく、1段目の外部レビューを検証して1本に統合する担当も兼ねます。突き合わせの方針は [guidelines/review_guideline.md](../../../guidelines/review_guideline.md) セクション4 が正本です。

出力は**リライト案1本**とし、ユーザーが2本のレビューを自力で突き合わせなくて済む状態にします。

## 参照してよいもの（コンテキスト分離）

- [guidelines/review_guideline.md](../../../guidelines/review_guideline.md)（必須）
- [guidelines/style_profile.md](../../../guidelines/style_profile.md)（蒸留済みの場合）
- **当該サイクルの** `draft.md` と `review_external.md`
- 直近の公開版レポート2〜3本（`reviews/*/final.md` の新しいものから。ここでの新しさは山行日基準。足りなければ `corpus/` の新しいものを補充）
- タグ検索で選んだ類似条件の公開版1〜2本（手順3参照。`corpus/*.md`・`reviews/*/final.md` の frontmatter（タグ）だけの横断検索は可。本文まで読むのはこの1〜2本に限る）

**上記以外は読まない。** 特に、**過去サイクルの** `review_external.md` / `review_claude.md` / `review_gemini.md` / `notes.md` は参照せず、`corpus/` と過去 final の本文を上記の範囲を超えて読まないこと（CLAUDE.md「参照の原則」）。過去のレビュー結果への追従ではなく、ガイドラインだけを根拠にレビューすることで、メタレビューによる改善ループを機能させます。

## 手順

1. **対象サイクルの特定**: 引数でサイクルディレクトリが指定されていればそれを使う。指定がなければ、`reviews/` 直下で最新（ディレクトリ名の日付降順。日付は山行日を表す）かつ `review_claude.md` 未作成のものを候補として提示し、ユーザーに確認する。`draft.md` を Read する。
   - `review_external.md` が無い場合は、`/prepare_external_review` → `/register_external_review` の順で先に外部レビューを取り込むよう案内する。ユーザーが「今回は外部レビュー無しで進める」と明示した場合に限り、手順5〜6（突き合わせ）を省略した単独レビューとして実行し、frontmatter に `external_reviewer: none` を記録する。
2. **重点ポイントの確認**: ユーザーから「レビュー時に重点的に見てほしいポイント」「自分が気にしているポイント（うまく文章が組み立てられない、表現がうまくできない等の悩み）」といったコメント（任意）があるか確認する。
   - 引数や会話でコメントが渡されていればそれを使う。`draft.md` の frontmatter に `review_focus` があればそれも読み込む。
   - どちらも無い場合は、レビュー開始前に一度だけ「重点的に見てほしいポイントや気になっている点はありますか？（任意。無ければこのまま進めます）」と確認する。無ければそのまま進める。
3. **参照資料の読み込み**: 上記「参照してよいもの」のうち、ガイドライン・文体プロファイル・過去の公開版を読み込む。**この時点では `review_external.md` を読まない**（手順5まで開かない）。style_profile.md が未蒸留の場合はその旨を認識し、直近の公開版から文体を読み取る。
   - **類似レポートのタグ検索**: draft.md から山行条件（天候・眺望・難度・行程タイプなど [docs/tags.md](../../../docs/tags.md) の軸）を読み取り、`corpus/*.md` と `reviews/*/final.md` の frontmatter の `tags` を Grep で横断検索して、条件の近い公開版を1〜2本選んで読む（直近の公開版と重複したら追加は不要。明確に条件が近い回がなければ無理に選ばない）。文体・構成の参考とするのが目的で、事実関係を過去レポートから持ち込まない。

### 第1段: 自前レビューの作成（外部レビューを読む前）

4. **Claude 単独のレビューを作る**: 草稿とガイドラインだけを根拠に、指摘一覧とリライト方針を作る。ガイドラインに従い、特に核（不変層）は必ず守る。
   - セクション構成・順序を変えない
   - 山行の事実（日付・ルート・山名・天候・所要時間・出来事）を変更・創作しない。疑義があれば指摘一覧で確認を促す
   - 表現の細部に踏み込む「ほぼ全文リライト」を行う
   - 著者の語り口（文体プロファイル）から外れない
   - ユーザーからの重点ポイント・悩みのコメントがあれば、レビューにあたっての考慮事項とする（該当箇所を重点的に確認し、指摘一覧とリライト案で具体的に応える）。ただし核（不変層）やガイドラインを上書きするものではない
   - **この段階の指摘一覧（対象箇所・理由・修正提案・観点名）を、外部レビューを開く前にスクラッチパッドへ書き出して固定する**（例: `<scratchpad>/claude_first_pass.md`）。アンカリング防止のための工程なので省略しない。

### 第2段: 外部レビューの検証と統合

5. **外部レビューの読み込みと検証**: `review_external.md` を Read し、ガイドライン セクション4に従って検証する。
   - **核違反の検出を最優先**: 事実の創作／セクション構成の変更／部分添削で終わっている／文体からの逸脱／演出・誇張の過剰を洗い出す。該当するものは内容の良し悪しにかかわらず不採用とする。
   - **3判定**: 外部の各提案を **採用推奨 / 条件付き採用 / 不採用** に判定し、理由を必ず添える。「条件付き採用」は、何をどう調整するかまで書く。
   - **対応付け**: 手順4で固定した自前の指摘と突き合わせ、`[両者一致]` / `[外部]` / `[Claude]` に分類する。**外部が触れていないことを理由に、自前の指摘を取り下げない。**
6. **統合**: 統合指摘一覧を作る。番号は通しで振り直し、各項目に出所ラベルを付す。外部由来には元番号を `（外部#3）` の形で併記する。リライト案は**自前のリライトを土台**とし、採用推奨・条件付き採用と判定した外部提案を取り込む。外部のリライト全文をそのまま採用したり、2本並置したりしない。
7. **出力の構成**: ガイドライン セクション3の形式に従う。
   1. 総評（3〜5行。重点ポイントのコメントがあった場合は、それにどう応えたかにも触れる）
   2. 外部レビューの検証結果（核違反の指摘を先頭に。各提案の3判定と理由。件数の内訳も示す）
   3. 統合指摘一覧（番号付き。出所ラベル / 対象箇所の引用 / 理由 / 修正提案 / 根拠となるガイドラインの観点名。外部由来でガイドラインの観点に当てはまらないものは「観点: ガイドライン外」と明記する ── メタレビューが彩りの新規候補として拾うための情報）
   4. 全文リライト案（セクション構成維持。`［※指摘N：…］` マーカーは統合後の番号で埋め込む）
8. **保存**: frontmatter を付けて `review_claude.md` として Write する。
   - `reviewer: claude` / `reviewed_at` / `guideline_updated_at`（ガイドライン変更履歴の最新日付）
   - `external_reviewer`（`review_external.md` の `reviewer`。外部レビュー無しで実行した場合は `none`） / `external_model`
   - `external_verdicts`（`採用推奨` / `条件付き採用` / `不採用` の件数）
   - 重点ポイントのコメントがあった場合は `review_focus` にその要約も記録
9. **報告**: 統合後の指摘件数（内訳: 両者一致 / 外部 / Claude）と、外部レビューの3判定の件数、核違反があればその要点のみ簡潔に報告する（全文はファイル参照とする）。
